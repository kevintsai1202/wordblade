# 10/29 AI 導演改版：先理解、再規劃、經審查、最後給人確認（P1-1 改版，spec §5.11）

開發者 2026-10-29 看範例成片後的回饋：吉祥物進場不知道目的；打字的地方應該放大該內容；3D 桌面沒有轉場的意義，只是把原本的畫面放進桌面。
這些應該是 AI 導演的職責——先理解逐字稿、分析畫面，規劃整體內容，再開始編輯；並加一個審查腳本的角色來確認。

## 1. 現況與問題

現在的導演（10/28）：Spark 逐段（約 2 分鐘）看 480p 影片＋逐字稿，回段落報告 → Wonder 把各段報告整理成建議清單（6 種：cut、mask、fix、zoom、effect、camera）→ 閘道用固定規則檢查一次 → 使用者逐條採用。

| 問題 | 原因 |
| --- | --- |
| 建議彼此沒有關聯、看不出目的 | Wonder 拿到的是各段零散的報告，沒有整支片的結構（分幾段、每段在做什麼） |
| 放大沒有對準打字的地方 | 放大框是模型用眼睛估的固定位置，不會跟著游標或新出現的文字移動 |
| 3D 場景像是隨便放 | 提示詞只寫「放在大段落開頭」，沒有要求對準換段那句話、也沒有人檢查 |
| 吉祥物出現沒有理由 | 範例打包腳本寫死時間放的（不是導演提的）；導演的清單裡也沒有「指向什麼」的要求 |
| 沒有人把關 | 只有閘道的格式規則（時間、欄位、重疊），沒有檢查「合不合理、對不對得上旁白」 |
| 只管剪輯，不管整體 | 字幕樣式、配樂、片頭不在導演的範圍，要使用者另外做 |

## 2. 新流程

```
① 準備（本機，不花錢）
   逐字稿（沒有就先跑 Muse ASR）＋ 縮圖（已有的漸進式縮圖）＋ 畫面變化圖（比對前後縮圖，找出哪裡在打字、哪裡在動）
        │
② 理解（Muse Spark，逐段看影片；沿用現有的段落報告，加欄位）
   每段：摘要、段落結構（小節＋標題＋起訖）、重講與口誤、隱私項目、聽錯的詞、
        重點時刻（旁白哪一句、畫面上是什麼）、確認畫面變化區是什麼（「在 index.js 打第 7～12 行」「終端機印出結果」）
        │
③ 規劃（Muse Wonder，看全部段落報告＋畫面變化圖）
   寫「剪輯腳本」：先寫全片大綱（3～6 個章節），再列每一項編輯，每一項都要有：
     目的（為什麼）、對應的那句旁白（引用原文＋時間）、所屬章節
   範圍：剪、改字、遮罩、放大（跟著打字移動）、2D 特效、3D 轉場、字幕樣式、配樂、片頭標題
        │
④ 審查（另一個角色：Muse Wonder 的獨立呼叫，換一份「挑錯」提示詞、不帶規劃者的上下文；看腳本＋大綱＋逐字稿＋每一項時間點的縮圖）
   逐項判定：保留／修改（附修改意見）／刪除，並指出漏掉的（例如沒遮到的隱私）
   → 有修改或刪除就交回規劃者改一輪（最多一輪），閘道的固定規則最後再檢查一次
        │
⑤ 給使用者確認（介面）
   依章節顯示剪輯腳本：每項的時間、做什麼、目的、引用的旁白、審查意見；預設勾選審查通過的
   「套用勾選的項目」一次套用（一次 Ctrl+Z 復原）；也可以照舊逐條採用
```

## 3. 各角色的規則

### 規劃者要遵守（寫進提示詞，審查者也照這份檢查）

- **每一項都要有目的與對應的旁白**；說不出目的就不要放。
- **剪**：只剪重講、口誤、長時間無聲；剪在句子邊界。
- **放大**：只放在「正在打字、或旁白提到畫面上的小字」的地方；放大框跟著畫面變化區移動（由畫面變化圖算出路徑，模型只決定要不要放、放多久）；同時間只放一個；倍率 1.5～2.5。
- **3D 轉場**：只放在**章節交界**，對準換章節的那句話（例如「Now let's write the main script.」），長度 3～5 秒、頭尾回到滿版；整支片最多 3 個、彼此相隔 30 秒以上；要寫出「從哪一章轉到哪一章」。
- **2D 特效**：對準旁白的重點句（例如「And there it is: three bullet points」），描述要具體（指向畫面上的哪個東西）；每 20 秒最多 1 個、整支最多 5 個；不和放大、3D 同時出現。
- **吉祥物**：只在「指向畫面上一個具體目標」時用，要給目標的位置與理由；整支最多 1 次。
- **遮罩**：每個隱私項目都要遮，涵蓋它出現的整段時間。
- **字幕樣式**：整支一個（例如教學片用逐字高亮）。
- **配樂**：一句配樂描述＋放在哪裡（片頭之後到片尾），音量低於旁白。
- **片頭**：建議片頭標題與副標（用不用由使用者決定）。

### 審查者檢查（逐項）

1. 目的寫了、而且說得通。
2. 引用的旁白和時間對得上（審查者看得到逐字稿）。
3. 該時間點的畫面支持這個編輯（看縮圖：放大的地方真的有字、特效指向的東西真的在畫面上）。
4. 規劃者的規則有沒有被違反（密度、3D 位置、重疊）。
5. 有沒有漏掉的：隱私沒遮、明顯的重講沒剪。

## 4. 「打字的地方放大」怎麼做

- 本機用已有的縮圖（每 1 秒一張、寬 320），比對前後兩張：差異大於門檻的像素 → 變化區的外框；連續幾秒都在同一帶變化 → 一個「活動區段」（時間＋外框路徑）。
- 活動區段送給規劃者（「42～58 秒，畫面右上方 index.js 編輯區在變化」）；Spark 在理解階段確認那是什麼（打字、終端機輸出、捲動）。
- 規劃者決定要不要放大；放大的路徑點直接用活動區段的外框中心（平滑過），框寬依外框大小，所以會跟著打字的位置走。
- 捲動（整片在變）不放大。

## 5. 資料與介面

- `Suggestion` 加欄位：`purpose`（目的）、`quote`（引用的旁白）、`chapter`（章節）、`review`（審查：通過／修改過／刪除＋意見）；新增種類 `transition`（3D 轉場，取代 camera）、`captionStyle`、`music`、`intro`。
- `Project.directorPlan`：全片大綱（章節標題與起訖）——介面依章節分組顯示。
- 介面（AI Director 頁籤）：
  - 進度顯示五個步驟（準備、理解、規劃、審查、完成）。
  - 剪輯腳本依章節分組；每項：勾選、時間、種類、做什麼、目的、引用的旁白、審查意見（被刪除的灰色、預設不勾）。
  - 「套用勾選的項目」：需要 AI 的項目（遮罩、2D 特效、配樂）依序跑並顯示進度；全部完成後是一次編輯。
- 範例打包腳本改成：問導演 → 套用審查通過的全部項目，不再寫死時間放特效。

## 6. 成本與時間（demo-2min）

- 理解：和現在一樣（約 2.8 萬 tokens／2 分鐘）。
- 規劃：Wonder 一次＋可能改一輪。
- 審查：Wonder 獨立呼叫一次（腳本＋逐字稿＋每項一張 640 寬縮圖，約 1～2 萬 tokens）。
- 全程預估 2～3 分鐘（現在約 2 分鐘）；花費約 US$0.1 以內。

## 7. 驗收

- 單元測試：畫面變化偵測（合成畫面：只有一塊區域在變 → 外框正確；整片在變 → 判為捲動）、腳本驗證與規則（3D 不在章節交界、密度超過、重疊 → 被擋）、套用勾選項目是一次編輯。
- 閘道測試（假模型）：理解 → 規劃 → 審查退回 → 規劃修正 → 通過的流程；審查刪掉的項目不會出現在結果。
- e2e（假閘道）：剪輯腳本依章節顯示、勾選與套用、一次 Ctrl+Z 復原。
- 實機（demo-2min）要看到：
  - 剪掉重講、遮住假金鑰、改正聽錯的 dotenv；
  - 寫程式的段落（約 43～60 秒）放大並跟著打字的位置；終端機印出結果時放大；
  - 3D 轉場只出現在章節交界，並對準換章節的那句話；
  - 特效對準「three bullet points」這類重點句；沒有目的的吉祥物不會出現；
  - 開發者看重新產生的範例成片，覺得每個效果都有理由。

## 9. 開發者決定（2026-10-29）

1. 審查者用 **Muse Wonder**，但是**另開一個獨立的呼叫**：只給它剪輯腳本、大綱、逐字稿與縮圖，不帶規劃時的對話與推理，避免被規劃者的上下文影響。
2. 字幕樣式、配樂、片頭標題**由導演規劃**。
3. 吉祥物**交給導演規劃**（照第 3 節的規則：指向具體目標、寫出理由、整支最多 1 次）。
4. 「套用勾選的項目」**預設勾選審查通過的全部**。
5. **不砍 P1**：時間足夠，導演改版做完照順序做 P1-9、P1-10、P1-14。
